Six real examples

One folder per harness. Same controls on every one.

For the five frameworks airlock extracts the agent's tools and drives the loop itself (OWN mode) — so guards, approvals, routing, fallback, skills and traces all apply. A plain callable is Terminal (observe-only) — the honest contrast.

The headline feature

Skills on / off — flip the YAML, change what the agent can do.

Every example exposes a uniform two-tool contract. A skill maps a tool to the public surface with an enable switch. Disable it and it's gone from the typed endpoint and dropped from the agent's loop — identically on every harness.

# worker.yaml skills: calc: { tool: multiply, enabled: true } # POST /skills/calc → 200 danger: { tool: danger, enabled: false } # POST /skills/danger → 403 + dropped from the loop $ curl -s -o /dev/null -w '%{http_code}\n' -X POST localhost:3101/skills/calc # → 200 $ curl -s -o /dev/null -w '%{http_code}\n' -X POST localhost:3101/skills/danger # → 403 $ curl -s -o /dev/null -w '%{http_code}\n' -X POST localhost:3101/skills/nope # → 404
What airlock owns

Control the loop — the part a gateway in front of the agent can't.

Because airlock drives the loop instead of proxying it, these act during a run. The showcase exercises them live.

🔨 Tool extraction

The framework contributes its tools; airlock runs the loop. No adapter to write.

🔀 Model routing & fallback

Switch models per request; retry then rotate to a backup when one fails.

✋ Mid-run approval

Hold a sensitive tool for a human — approve, edit, override, or deny.

📊 Live step trace

Every model call, tool call and result — streamed with tokens, cost, latency.

🔒 Per-tenant isolation

State, sessions and runs scoped to the authenticated tenant — structurally.

🧯 Graceful failure

An upstream model error is a clear 502, never a bare crash.
